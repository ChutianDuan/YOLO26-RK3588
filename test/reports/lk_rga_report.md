# LK 的 RGA / DMA-BUF 对比实验

## 交付结论与默认选择

已接入 RGA3：OpenCV BGR → 可复用源 DMA-BUF → 同步 RGA 缩放/转 NV12 → CPU 直接读取 mmap 的 Y 平面执行 LK。没有再生成独立 CPU 灰度 Mat；CPU 仍执行特征、金字塔和双向 LK。检测 Worker、模型、类别和输出坐标契约保留。

默认配置为 `lk_preprocess: rga`、`lk_scale: 1.0`，保留原有跟踪分辨率。`lk_scale: 0.75/0.5` 为显式缩图选项；`lk_preprocess: opencv` 保留 CPU 对照。

下面是同版本异步动态流程的整段视频实测，各配置/模型各一次；Flow 单位 ms/解码帧，包含全部灰度准备、LK 和运动补偿。

| 指标 | CPU 原分辨率 | RGA 原分辨率（默认） | RGA 0.75 倍 | RGA 半分辨率 |
|---|---:|---:|---:|---:|
| FP16 Flow | 65.464 | 64.982 | 50.236 | 38.864 |
| FP16 处理 FPS | 12.59 | 12.63 | 15.56 | 18.90 |
| FP16 跟踪 F1 | 58.17% | 55.83% | 56.09% | 55.09% |
| INT8 Flow | 45.080 | 44.605 | 34.719 | 26.190 |
| INT8 处理 FPS | 16.98 | 17.10 | 20.58 | 24.96 |
| INT8 跟踪 F1 | 37.69% | 38.20% | 37.59% | 38.19% |

原分辨率 RGA 的 Flow 与 CPU 很接近，不能宣称把 LK 算法硬件化后取得加速。缩小图像确实降低了计算量，CPU 半分辨率对照同样明显变快；主要收益来自减少特征和光流工作量。

固定相同检测帧时，RGA 半分辨率的 F1 高于 CPU 原图；异步时 FP16 F1 反而有下降。默认保留原分辨率，避免新增缩图带来的算法尺度变化；这不保证 RGA 与 CPU 异步跟踪精度等价。RGA 原图在本片段的异步 F1 也低于 CPU。灰度舍入、检测/回传时机、结果帧间隔和动态步长都可能影响结果，尚未隔离单一原因。

FP16 CPU 原图的两次固定对照 Flow 为 94.416、66.746 ms，RGA 半图为 52.004、51.882 ms；保留均值和每次结果，不隐藏波动。CPU/NPU 没有锁频/绑核，不将跨时段差异完全归因于 RGA。只验证该视频；没有新的模型 mAP、IDF1/HOTA 或多场景精度验收，也未达到源视频约 30.11 FPS 的实时吞吐。

编译、运行、检查和性能分别记录：原生 C++17 Release 构建通过；CTest 3/3 通过（21.35 秒）；22 次整段视频共 26620 帧；14 次固定调度均为相同 152 个源帧且原始检测框逐字段一致；8 次异步运行完成队列/历史/EOF 和帧归属检查。

3000 帧附加内存检查通过：稳定阶段 RSS 142.52 → 140.96 MiB，变化 -1.55 MiB。只说明本次时长与输入未持续增长。模型与材料包哈希保持一致；动态链接不含 Conda、ONNX Runtime、OpenVINO、Drogon。SDK 与系统配置未修改。

验证记录位于工程根目录下 `validation/lk_rga_20261018/ctest-final.log`、`checks.json`、`environment-final.json`、`ldd.log`、`dataset-integrity-final.log`、`soak_full/report.json`。早期 `fixed` 目录是 Y400/imfill 试跑，遇到 RGA2 地址限制后已替换；不纳入这 22 次最终实现结果。

所有配置均使用 CPU 执行 LK；RGA 输出的灰度图通过 mmap 直接供 CPU 读取，没有再复制灰度图，也未实现端到端零拷贝。

实现：RGA3 将 BGR DMA-BUF 转为 NV12，LK 直接读取 Y 平面；宽高取最近偶数、stride 对齐 16，前后帧固定双缓冲并持有 DMA READ 租约。
RK3588 的 Y400 和 color fill 依赖 RGA2，system heap 的高地址页可能导致 no core match。最终实现避免 Y400，检测 padding 仅首次/几何变化时由 CPU 初始化为 114；两路 RGA 任务均通过单任务选项使用 RGA3，NPU 核心策略不变。
