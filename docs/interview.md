## 面试复习：项目介绍与问答

### 1 分钟介绍

> 我在 RK3588 上用 C++17 做单路摄像头检测和跟踪。YUYV 链路用 V4L2 导入 DMA-BUF，由 RGA 转成 RGB，再通过 FD 绑定给 RKNN；MJPEG 链路先用 MPP 解码为 NV12，将检测和输出分开调度。工程重点是缓存同步、帧租约和有界并发。针对 INT8 的量化损失，我先做 PTQ，再逐层比较误差，将敏感关键层保留为 FP16，得到 Hybrid 混合精度模型。它比 FP16 文件小约 42.62%，在三 NPU Worker 的单路回放长测中完成约 30.11 FPS 检测。Hybrid 的精度恢复幅度还需同帧 mAP 评测，所以链路正确性、性能和精度分别报告。

这段介绍描述工程事实。个人职责与团队分工请按实际经历说明，不将代码中存在的功能自动说成个人独立完成。

### 3 分钟展开

1. **场景与约束**：ARM64 板端、现有 Runtime 2.5.0 和 RGA/MPP SDK；模型在主机转换，板端原生编译，不依赖 CUDA/TensorRT。
2. **采集与预处理**：摄像头原生 800×600，模型 800×608。解释格式协商、帧池、DQBUF/QBUF、RGA 颜色转换和上下补 4 行。
3. **内存正确性**：FD 只描述 allocation，mmap 是 CPU 视图，设备导入和帧租约各有职责；Cache Sync 与 IM_SYNC/推理完成不能互相替代。
4. **实时调度**：MJPEG 解码后检测与输出共享只读租约，各自消费最新帧；固定线程、有界队列、时间水位拒绝迟到结果，Kalman 预测保证输出无需等待每次检测。
5. **量化与实测取舍**：PTQ 后逐层比较误差，关键层保留 FP16，其余适合的部分使用 INT8。Hybrid 文件为 12.17 MiB，比 FP16 小约 42.62%；相同约 30 FPS 回放下，10 分钟长测有效检测约 30.11 FPS、RSS 均值 146.17 MiB。结合原始计数、延迟与各核负载解释取舍。
6. **编码与发布**：画框后同步 RGA 写入独立编码 NV12 三槽池，由单 Worker 执行 MPP H.264；FFmpeg 免重编码发布给独立 MediaMTX。真摄像头三十分钟输出并编码约 29.96 FPS，解释编码完成延迟与观看端延迟的区别。
7. **后续工作**：补充 Hybrid 与 FP16/INT8 的同帧精度评测、工业场景覆盖、观看端延迟和更长时间/异常恢复测试，再评估多路与跨网部署。

### 常见追问

**DMA-BUF 为什么能减少复制？**

它让不同设备通过 FD 导入同一底层 allocation，省去某些应用层搬运。它本身不保证驱动支持、格式匹配、连续物理地址或端到端零拷贝。本项目 YUYV 稳态上传与 MJPEG 压缩包应用层复制均为 0；包尾清零、文件上传、CPU 画框及内核内部复制需分别核对。

**DMA-BUF 的 mmap 是不是复制？**

mmap 只建立 CPU 虚拟地址映射。生产摄像头链路统一使用 DMA-BUF，已删除原 MMAP/copy 模式；文件 BGR 仍有一次上传。

**shared_ptr 是否能保证硬件访问安全？**

它可以保持 allocation 活着，但设备可能还没完成，也可能另一线程准备写入下一帧。本项目还用帧租约阻止复用，并在 RGA 完成、RKNN 完成之后释放相应租约。

**源缓冲什么时候 QBUF，为什么无需等 NPU？**

YUYV 源由 RGA 读取；同步 RGA 完成后，NPU 使用独立 RGB 目标，因此源可归还。目标 RGB 必须保留到推理结束。

**为什么不把所有任务塞进无限队列，避免丢帧？**

实时场景积压会导致处理越来越旧的画面并增加内存。本项目保留最新等待项，记录丢弃原因；已经执行的任务通过租约保护。对不可丢的结果/写出使用小容量队列和明确超时。

**三个 NPU 核是否让一个模型快三倍？**

不能这样推导。单 Context 绑定三核的 `all` 在当前模型上甚至更慢；`split` 是三个独立 Context 对不同帧并发，提高吞吐并消耗更多内存。需要单次耗时、实际检测 FPS、校正年龄和 RSS 一起比较。

**画面 30 FPS 就等于每帧有最新检测吗？**

不等于。default 的历史输出约 30 FPS，而检测约 22 FPS；中间画面依靠快照预测。要同时报告输出帧率、检测帧率和校正数据年龄。

**RGA 是否加速了 LK？**

RGA 负责灰度转换与缩放，LK 算法仍在 CPU。原分辨率收益有限，半分辨率的主要收益来自工作量减少；还要检查 F1 和尺度变化。

**INT8 精度为什么下降，如何定位？**

先确认同一权重、颜色/layout/归一化、letterbox、输出量化和后处理一致，再用相同标注帧对照 FP32/FP16/INT8。Hybrid 的优化流程是在主机 PTQ 后逐层比较浮点与量化结果，找到误差敏感位置，将关键层保留或恢复为 FP16，其余适合的部分保持 INT8。这样按层分配精度，兼顾降低量化损失与模型压缩；具体 mAP 恢复幅度还需要同帧评测，校准集覆盖和场景分布也需继续验证。

**Hybrid 中的“动态量化”具体指什么？**

指转换时依据逐层误差对比结果调整 INT8/FP16 的分配，最终固化为 RKNN 模型。板端使用既定的混合精度计算图；`split` 则是三个独立 Context 对不同视频帧并发推理，精度分配与 NPU Worker 调度分别处理。

**YOLO 为什么不用 NMS？**

当前 YOLO26 one-to-one 导出已经确定为双阶段 Top-K 契约，不能擅自添加影响结果的 NMS。更换导出或 YOLO 版本后重新校验。

**你如何证明没有泄漏、性能达标？**

先限定输入、帧数和验收目标，记录预热后 RSS/FD、队列上限、丢帧、温度和时延分位数。已有三模型各 10 分钟、18066 输入帧的连续长测，以及真实摄像头三十分钟、53,988 输出/编码帧的推流长测；后者还核对了 39 个 DMA-BUF 退出后全部释放。这些分别说明给定条件下的有限测试结果，没有无限时长保证。没有设定工业精度目标时也不能宣称工业达标。

**为什么让 MediaMTX 独立运行？**

C++ 负责采集、推理、绘制、MPP 编码和 MPEG-TS；FFmpeg 发布 RTSP，MediaMTX 接收并分发。进程边界便于分别调试和重启，C++ 通过非阻塞本机 UDP 发送并使用有界编码槽。已实测 MediaMTX 或发布器重启时推理继续，服务恢复后可重新拉流；浏览器使用 WebRTC。

**遇到过什么实际问题？**

可结合原始记录讲两个：cached heap 的外部 FD 输入切换不一致，最终采用 uncached 检测目标；同一底层缓冲的重叠注册与清理曾触发 NPU 超时，随后调整为先撤旧注册再导入，并通过 FD/dup/生命周期回归。区分观察、推断与最终验证，详见 [排查报告](../test/validation/rknn_dma_input/report.md)。
