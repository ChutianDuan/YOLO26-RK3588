# 后续开发与证据补齐路线

核对日期：2026-11-18（Asia/Shanghai），以当前工作区为准。这里列出尚未完成的工作，不把已实现的多路预测、COCO640 或平移防抖继续列为待开发功能。运行入口见 [项目 README](../README.md)，现有架构见 [设计图](design-diagrams.md)。

当前日常回归按 `cpu` 标签选出九项纯软件测试，完整套件 28 项。最新历史验收见 [报告索引](../test/reports/README.md)。28 项通过、约 30 FPS 输出与工业精度达标是不同结论。

## 1. 修正评测时间索引

当前 [validate_camera_live.py](../test/tools/validate_camera_live.py) 的真值/预测以源帧 `0,6,12…` 为键传入 `tracking_metrics()`；[材料评测器](../test/rknn_video_compare_20261018_002d290d/tools/evaluate_bdd100k_tracking.py) 用 `frame_index-1` 判断相邻标注。历史 CPU 最小例子已观察到连续漏检段和 fragment/jitter 统计受到影响；这不能扩大为全部 AP/IDF1 均错误。

下一步在项目适配层依据固定 `frame_map` 重建完整标注时刻，保留源帧号追溯；不能按实际输出记录重新编号并抹掉缺失时刻。回归覆盖非单位 stride、连续漏检、断续可见与连续匹配。修复后另建报告目录，记录受影响字段和修正前后差异，不覆盖材料包或历史证据。

防抖已引入坐标域变化：精度与三模型历史对照工具现显式使用 `--stabilize off`，保持完整原图。未来评估默认防抖模式时，要按每条 detection/frame 自身 ROI 逆映射并限定可见区域，再与真值比较。

## 2. 补齐 Hybrid 精度与转换来源

复用 [compare_split_precision.py](../test/tools/compare_split_precision.py)，把当前 FP16/INT8 清单参数化并加入 Hybrid。固定相同 202 个标注时刻、相同图像/几何、阈值和评测器，要求每个模型覆盖 202/202；实时性能实验另测，避免丢帧改变精度样本。

主机转换材料仍需归档权重/ONNX 哈希、Toolkit2 版本、校准清单/哈希、逐层误差、敏感层与混合精度配置。板端已有模型文件与性能结果不能独立证明这些主机步骤，更不能证明 mAP 已恢复。现有单条 BDD100K training 序列仅作回归；新增场景按视频/机位划分校准与评测，避免相邻帧泄漏。

当前已有双输出模型的配置化校验；后续可增加明确的模型清单记录颜色、layout、预处理、类别、TopK 与导出来源，并逐项与 Runtime 属性对照。单输出 e2e 若要接入，需独立输出适配及同输入结果/精度/性能对照，不能直接加载到双输出引擎。

## 3. 当前版本的并发与性能对照

分别比较 `camera_live` default/all/split、`yolo_multi` 1/2/3/4 路、录像开关、检测频率以及防抖开关。固定模型、输入、统计窗口和输出负载，记录真实检测 FPS、不同源画面 FPS、输出 FPS、检测年龄、P95/P99、CPU/NPU、RSS/PSS/FD、丢帧与温度。

历史四路约 52.67 次/秒总检测吞吐来自旧版基线；四路各 30 次真实检测需要约 120 次/秒，现有证据不支持该目标。当前版本有 120 秒预测运行和近期完整功能回归，但仍需同条件较长多路性能测试。单路 `yolo_multi` 受每路一个在途约束，不能直接用三个 Worker 推导单路三帧并行。

防抖最近的 COCO FP16 3000 输出帧实测约 29.98 FPS 输出、14.31 FPS 实际检测，现场大面积遮挡导致多数帧失锁；需要有足够静态纹理背景的真实抖动场景，另测有效估计率、残余抖动与跟随体验。可重复硬件回放的 RMS 降低不替代该现场验证。

## 4. H.264 文件硬解，再接 RTSP 输入

建议顺序：系统 libavformat 解封装 → 有界压缩输入 → 既有 MPP → 携带 PTS/颜色信息/租约的 NV12 → RGA/RKNN/跟踪/输出。先验证一个明确 H.264 profile、分辨率和色彩组合，再扩展。

当前 MJPEG 每图独立，可替换压缩包 latest 等待槽；H.264 有参考依赖，不能任意丢压缩包。应保持解码连续，主要在解码后的 NV12 丢旧保新；压缩输入预算耗尽须明确背压/重建策略。MPP 的参考帧、info-change、EOS、PTS/DTS、stride 和 CPU 参考都需单独验证，不能照搬 MJPEG 八槽规则。

RTSP 首版从可控 TCP 输入开始，设计连接/读取/停止超时与 backoff；会话 epoch 必须贯穿检测任务、结果和快照，旧会话迟到结果不得校正新 Tracker。分辨率、时间戳、颜色矩阵或范围变化要明确处理/拒绝，不能继续固定假定 BT.601。

验收顺序为单路文件像素/PTS对照、本机可控 RTSP 断流恢复、实际网络摄像头，再做多路。缓冲释放必须同时满足 MPP 参考持有、应用帧租约与设备完成，`shared_ptr` 或 Cache Sync 不能代替这些条件。

## 5. 把稳定性证据变成可执行条件

为明确场景设定逐路最低检测率、结果年龄 P95/P99、允许丢帧、RSS 趋势、FD 平衡和温度预算；阈值先根据场景与基线确定。先短测和故障回归，再做当前版本 600 秒、30 分钟及必要时更长运行。

故障矩阵包含慢推理/输出、队列满、EOF/SIGINT、写盘失败、输入断流/会话时间跳变、编码失败隔离与反复启停。软件注入与真实拔插、驱动故障分开记录。结果/日志队列的 250 ms 仅限制入队等待；同步 I/O、join 和驱动阻塞尚无统一硬超时。

每次实验保存源码版本/脏状态、二进制/模型/输入/配置/SDK 哈希、完整命令和统计区间。历史 10 分钟/30 分钟记录继续保留为对应版本证据，不替代当前版本、工业精度或无限时长保证。
